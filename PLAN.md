### The prompt: role, context and goal

You are the maintainer preparing `triage` for its first public release. The owner, Abhigyan, runs it daily and will keep running it throughout; he reviews after each phase. Work in `~/triage` on the Mac (connected folder; the VM shell on the Mac runs Python 3.10 with `PYTHONPATH=src` for tests; the Mac's own venv runs the real thing).

What triage is: a Python 3.10+ package (about 5,900 lines in `src/triage/`, 56 tests, four prompts) that keeps a BazQux unread list worth reading. Every 30 minutes a launchd job runs `triage run`: it fetches new articles through the Google Reader API, sends them in batches of 20 to a teacher model (Claude Sonnet 5.5, Message Batches API, a cached prompt prefix) that judges each as teaching material for one student on five sub-scores, stores the judgment once, tags the article `score-90` to `score-0` in BazQux, and, when enforcing, marks the worst read. A second model (Opus 5.5) re-reads close calls; a third pass (Haiku 5.5) is a cheap stand-in for blasts over a backlog. The student teaches it back through stars, reads, and verdict tags (`great`, `good`, `meh`, `bad`, `basic`, `heavy`, `more`, `less`), which feed the teacher's concept lists every call and a weekly rewrite of a learner model by Opus, with an eval gate and guardrails. Around it: a manual prune with a concept cap, undo, bankruptcy, a dead-man heartbeat, a static dashboard, a live progress view, a control room on 127.0.0.1:8766, and `triage status`, `stop`, `halt`, `schedule`, `enforce`. Modules: `bazqux` (client), `ids`, `store` (SQLite), `teacher` (LLM, judgments, batches, cost), `cut`, `feedback`, `learner`, `pipeline`, `progress`, `dashboard`, `report`, `control`, `panel`, `ops`, `config`, `cli`, `replay`. Read `README.md`, `RUNBOOK.md` and the project design doc before touching anything.

The goal: a repository a stranger can clone, install with `pipx`, point at their own BazQux account and Anthropic key, and run with confidence, understanding in ten minutes what it does, what it costs and how it learns them; code that reads as one hand wrote it, with nothing of the owner's identity baked in; tests and CI that make a contribution safe to merge; a command set and a dashboard that are a pleasure to use; and the owner's own install migrated without a day's interruption. Clean and robust first, features second: a smaller, clearer tool that never loses an article beats a larger one.

### Constraints that hold throughout

1. Never miss a good article. Every change to scoring, cutting or feedback fails open: when in doubt an article stays unread. No change to the scoring contract (weights, caps, bands) without the owner's yes; a prompt text change bumps `prompt_version` only if it should re-judge the unread pile, and you say which.
2. Simple and robust beats clever. No new runtime dependency without a reason written in the commit; no web build step, no JavaScript framework, no database other than SQLite, no background process other than the schedule the operating system runs (launchd, systemd, Task Scheduler, or the portable `serve` loop where none exists) and the console. Fewer moving parts than today is a success.
3. Secrets stay secrets. Never read, print or commit `.env`, `data/`, `profile/` or `dashboard/`; name variables, never values. Audit every log line, error message, dashboard field and API payload for emails, tokens, keys and the BazQux auth header. The control room keeps binding to 127.0.0.1 and refusing POSTs without its header.
4. The owner's install keeps running. Config, database and tag names migrate automatically on the next run (a `schema_version` key, an explicit migration per change, tested); renamed launchd labels are unloaded by the installer; old tag names stay accepted for one release. A phase that would interrupt the 30-minute cycle says so before it starts.
5. Economical. No change may raise cost per 1,000 judged above today's figure (about $0.65 in batch mode); every call to a model goes through the batch path and the cached prefix wherever the provider offers them; `doctor --live` keeps costing cents.
6. Everything verifiable. Each change comes with a test; `pytest -q`, `ruff check`, `ruff format --check` and `mypy` pass before every commit; the live checks the session cannot run are listed for the owner with the exact command and the expected output.
7. One voice. Code, docstrings, help text and docs read as the existing ones do: plain words, full sentences, no jargon, no emoji, no exclamation marks, British or American spelling as each file already has it (pick one in Phase 3 and apply it).
8. Git discipline. One branch `oss`, one commit per theme with a message that explains why, trailers `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>` and `Claude-Session: <this session's link>`; never rewrite published history; tag `v1.0.0` only in Phase 10.
9. Ask before: deleting any file that is not clearly dead, changing a tag name people may have in BazQux, changing the DB schema in a way that cannot be rolled back, or spending more than $1 on live checks.

10. Performance. A fixture database of 50,000 articles built by a script; the pending query under 100 ms, a run's non-network phases under 5 s, the dashboard render under 1 s, `find` under 200 ms; measured in CI on Linux and reported, failing only on a 3x regression.

12. Time. All stored times UTC ISO; local time only for display and the budget's midnight; a test that runs the budget across a DST change and across `Asia/Kolkata`.
13. Dependency hygiene. Lower bounds on every dependency, upper bounds on the SDKs (`anthropic<1`, `openai<2`) because their APIs move; `pip-audit` in CI; the SDKs pinned to a tested minimum in CI's matrix (oldest supported and latest).
14. CI on GitHub Actions: `ubuntu-latest`, `macos-latest` and `windows-latest`, Python 3.10 and 3.13: `ruff`, `mypy --strict`, `pytest --cov`, `pip-audit`, the `pipx install .` smoke test (`NAME version`, `NAME init /tmp/t`, `NAME doctor`), the generated `CONFIG.md` fresh; a scheduled weekly run against the newest SDKs and the evals. Badges in the README. No test may depend on the network, the clock or test order; flaky tests are fixed, never retried.
15. The live checks the session cannot run, written as a checklist for the owner at the end of the phase: `NAME doctor --live` (expected lines), one `NAME run --sync --limit 20` (expected summary), a `NAME catch-up --model <quick model> --max-seconds 60` on a few hundred, `NAME backup`, the console's buttons once each.

### Phase 5: models, keys and providers

Outcome: any model from any of five providers fills any of the four roles, chosen in `config.yaml` as `provider/model`, including models released after this code was written; keys live in `.env` or the keychain and are checked by `doctor`; switching a model is safe, measurable and reversible.

1. Roles, not models. Config names four roles: `models.judge` (every article), `models.reviewer` (the close calls, full text; the one that decides), `models.profiler` (the weekly profile rewrite), `catch_up.model` (the quick judge for a backlog). Each is a string `provider/model-id`, for example `anthropic/claude-sonnet-5-5`, `openai/gpt-5`, `gemini/gemini-2.5-pro`, `openrouter/qwen/qwen3-235b`, `ollama/llama3.3`. No allow-list: an unknown model id is passed through, probed once by `doctor --live`, and recorded with every score it produces.
2. One provider interface. `providers/base.py` defines `Provider` with `judge(system, user, schema) -> text`, `complete(system, user) -> text`, `submit_batch(requests) -> id`, `batch_status(id)`, `collect_batch(id)`, `capabilities() -> {batch, structured_output, prompt_cache, max_context}`, `usage -> tokens` and `price(model) -> (in, out, cache_read)`. `providers/anthropic.py` keeps everything that exists today (batches, 1h cache, structured output, the fallbacks); `providers/openai.py` (Responses API with JSON schema, the Batch API), `providers/gemini.py` (JSON mode, batch), `providers/openai_compatible.py` with a `base_url` (OpenRouter, Ollama, LM Studio, vLLM, anything that speaks the Chat Completions shape). A provider without batches runs the sync path with `limits.parallel_calls`; without structured output it gets the plain-JSON prompt and the lenient parser; without a cache nothing is lost but money. The run never knows which provider it is talking to.
3. ### The design system

Outcome: every colour, size and distance on the page comes from a token defined once in `html.py` (the one HTML layer of the open-source plan's Phase 3) and emitted as CSS custom properties; nothing is hard-coded in a template or a script; light and dark are two value sets of the same tokens, each validated.

1. Colour roles, each a token: `--surface-1` (page), `--surface-2` (cards, table stripes), `--text-primary`, `--text-secondary`, `--text-muted`, `--line` (hairlines), `--accent` (one hue: links, the current section, the progress bar, the selected filter), `--accent-wash` (the accent at 10% for selection and hover), status `--good`, `--warning`, `--critical` (reserved for state, always with an icon or a word, never for a series), and the band scale `--band-90`, `--band-70`, `--band-50`, `--band-30`, `--band-0`: one hue stepped light to dark for an ordered scale (more is better reads as darker), with a text-safe companion for each step where a band is written as a chip. The de-emphasis grey `--series-muted` for context series in emphasis charts. Dark values are selected steps of the same ramps against the dark surface, declared under both `prefers-color-scheme: dark` (guarded so a light stamp wins) and `[data-theme="dark"]`; the page honours the OS and offers no toggle of its own beyond a `data-theme` hook the Mac app may set.
2. Validate the palette, do not eyeball it: the five band steps and the status trio must pass the lightness band, chroma floor, adjacent-pair colour-vision separation (OKLab ΔE ≥ 8 adjacent), normal-vision floor (≥ 15) and contrast checks in light and in dark; run the data-visualization validator (`validate_palette.js` from the dataviz method, with `--ordinal` for the band ramp) when the session has it, and record the report in `docs/design.md`. Text never wears a series colour; a chip's text is `--text-primary` on a wash of the band colour, and the band's name is always printed beside the colour.
3. Type: the system stack; sizes on one scale: 13 (table body, captions), 15 (body), 17 (section lead), 22 (section title), 48 (the hero figure, proportional figures, semibold); line heights 1.45 for prose, 1.25 for headings; `font-variant-numeric: tabular-nums` in table columns and axis ticks only; sentence case everywhere; no all-caps labels; weights 400 and 600 only.
4. Spacing on an 8-point scale (4 for inner chips): 16 inside cards, 24 between elements, 48 between sections; a content column of 720 px for prose and the list, 1100 px for tables and charts that earn the width, centred, 16 px side gutters on the phone; no card inside a card; cards only where grouping needs a boundary (stat tiles), otherwise whitespace and a hairline.
5. Shape and depth: 8 px radius on tiles and chips, 4 px on buttons and inputs; no shadows (a hairline `--line` border and the surface step do the work); no gradients; icons are a small inline set drawn as 16 px SVG paths (run, pause, stop, star, link, chevron, warning), stroke 1.5, currentColor.
6. Density: one table row 36 px on desktop, 44 px tap targets on the phone; tables under 640 px become stacked cards with the label and value pairs; charts keep their axis band inside their box so no inner scrollbars appear.
7. States, all designed, none left to chance: loading (a quiet skeleton on first paint only), refreshing (the previous render held at reduced opacity, no layout jump), stale (the "updated 12 min ago" stamp turns to `--warning` after two cycles and says why), empty (a sentence that says what will appear and what causes it), error (the engine's own plain sentence and the one action that helps), offline (the static export marks its time and that it is a snapshot).
8. Motion: 150 ms ease-out on opacity and transforms only; the progress bar's live animation and the sparkline's draw-in respect `prefers-reduced-motion` (then they just appear); nothing blinks, nothing scrolls by itself.
9. Accessibility built in: landmarks (`header`, `nav`, `main` with one `section` per question, each with an `h2`); a skip link; visible focus rings (`--accent`, 2 px, offset 2 px) on every interactive element; every table with a `caption` and `th scope`; charts as `figure` with a `figcaption` that states the finding and a "Show as table" toggle that reveals the data; colour never the only carrier (bands print their name, status has a word, the current filter has a check); contrast at AA for text and 3:1 for lines and icons; touch targets 44 px on the phone; the page reads in order without CSS.
10. The tokens, the type scale, the spacing scale, the icon set and the states live in `docs/design.md` with one screenshot per state, and in a `/design` page the console serves in development that shows every token and component on one screen (the living style guide the visual tests screenshot).

### Charts: the rules for every chart on the page

The page has four charts (the stat-tile sparklines, the calibration bars, the grades grid, the spend columns) and one meter (the progress bar). Each follows the data-visualization method in this order: form first, colour by the job it does, the palette validated, marks and spacers to spec, a hover layer, a table twin, then look at the render. When the session has the `dataviz` method and its validator, use them; the rules here are the ones that bind either way.

1. Form by job: a single value with a trend is a stat tile, never a one-bar chart; a share by band is a bar (horizontal when the labels are words); a count over days is a column chart; parts of a whole are a stacked bar, never a pie; two measures of different scale are two charts, never a second axis. The flow chart of today (five grouped series over 14 days) becomes the four sparklines in the tiles plus the one spend chart; nothing on the page shows more than two series at once.
2. Colour by job: the band scale is an ordinal ramp of one hue, used for the chips, the grades grid and nothing else; a single series takes the accent; context takes `--series-muted`; status colours never appear on a series. Categorical hues are assigned in a fixed order and never cycled; this page needs at most two.
3. Marks: bars at most 24 px thick with a 4 px rounded data end and a square baseline; a 2 px surface gap between touching bars and stacked segments, never a stroke; lines 2 px with round joins; end markers at least 8 px with a 2 px surface ring; area fills at 10% opacity; grid and axes as solid 1 px hairlines one step off the surface, never dashed; axis ticks on round numbers, compact from 1,000 (1K, 2K).
4. Labels: a title that states the finding, not the topic ("Spend is under the budget every day this month"); direct labels selectively (the maximum, today, the end of a line), never on every point; a legend whenever two series share a chart, none for one; text in text tokens, never in the series colour; a label that does not fit moves outside the mark or to the tooltip, never clipped.
5. The hover layer ships with every chart: a crosshair snapping to the nearest day on the spend chart, a per-mark tooltip on bars and cells, the same readout on keyboard focus, a hit target of at least 24 px around small marks; values lead, labels follow in the tooltip; names inserted with `textContent`.
6. A table twin for every chart, behind "Show as table", carrying every value the chart shows; the chart is never the only way to read a number.
7. The sparkline: 7 points, the last in the accent with a ring, the rest in `--series-muted`, no axes, the tile's value and delta carry the numbers; 40 x 16 px on the phone, 72 x 20 on desktop.
8. The progress bar is a meter: the fill in the accent, the track a lighter step of the same hue; the numbers printed beside it, never only the bar.
9. No chart on the page animates data; a draw-in on first paint only, off under Reduce Motion.
10. Render and look: every chart has a Playwright screenshot in light and dark at 390 and 1280 px in the visual tests, and the review checklist (below) is applied to each before it is called done; anything matching the method's anti-pattern list (dual axes, recolour on filter, cycled hues, numbers on every point, clipped labels, a fixed height that cuts the axis, a pie for close values, colour-only encoding) is a failed review.

### Live behaviour, the data contract, performance

1. One document feeds everything: `GET /api/dashboard` returns `{schema: 1, as_of, state, today, list, verdicts, learning, feeds, money, machinery}` with every number the page shows and nothing it does not; the static export embeds the same document in a `<script type="application/json">` block and renders from it; the Mac app reads the same route. The document's JSON schema lives in `docs/json.md` and a test validates each render against it. Numbers arrive as numbers, dates as ISO strings, texts already composed by the engine (the state sentence, the attention reason, the calibration sentence), so the page never invents words.
2. Live updates: the console page subscribes to `/api/events`; a `progress` event updates the state line, the bar and the tiles in place; a `run_finished` event refetches the document; `attention` events update the banner; the page falls back to polling every 30 s when events are unavailable and says so in the footer. The export is a snapshot and says "Exported at 16:56; open the console for live data".
3. Freshness: "updated 12 s ago" in the header, ticking; after two missed cycles the stamp turns to the warning colour and the state line says the engine is not answering; the last render stays on screen at full opacity (it is still true) with the age made plain.
4. Refetch keeps the frame: on refresh the page holds the previous render and swaps nodes in place; no skeleton after the first paint, no scroll jump, no flashing numbers; a changed number briefly carries a wash that fades in 300 ms (off under Reduce Motion).
5. Budgets, enforced by tests: the HTML with its inline CSS, script and JSON under 200 KB for a 50,000-article database (the list capped at 50 rows, learnings and feeds capped); first contentful paint under 300 ms on a 2017 laptop; full render under 1 s; no request to any host but the console's own; the document built by the engine in under 250 ms at 50,000 articles (queries indexed, the heavy aggregates cached for 60 s).
6. Caching on the engine: the dashboard document is computed once per change (a run finishing, a verdict recorded, a settings change) and served from memory between; the export is written only after a run.
7. The page works without JavaScript: the server renders every panel from the same document; the script adds the live layer, the filters, the tooltips and the verdict menus. The filters and the "Show as table" toggles are plain links and buttons that work with the keyboard and without a pointer.

### Code architecture

Outcome: one place for the markup, one stylesheet, one script, one data document; the console page, the static export and the Mac app's web view are the same page with three flags.

1. `NAME/web/` holds `tokens.py` (the design tokens as a Python dict, rendered to CSS custom properties, the single source for the validator and the docs), `templates.py` (small functions that return HTML for each panel from a typed slice of the document: `header(doc)`, `today(doc)`, `article_list(doc, interactive)`, and so on, each under 60 lines, each escaping through one `esc`), `dashboard.css` (one file, under 600 lines, mobile first, no preprocessor), `dashboard.js` (one file, under 400 lines, plain ES2020, no framework, no build step: the event source, the renderers for the live parts, the tooltips, the filters, the verdict menu), `icons.py` (the inline SVG set) and `document.py` (builds the JSON document from the store: the only module that touches SQL, with one function per panel and the 60-second cache).
2. Three outputs from one render function: `render(doc, mode)` where mode is `console` (levers, verdict menus, the log, the live script), `export` (no levers, the embedded JSON, the snapshot stamp) or `app` (the console without the page chrome the Mac window supplies, with a `data-theme` hook). The test asserts the export equals the console minus a known set of nodes.
3. CSS written against roles, never values; class names by component (`.tile`, `.chip`, `.list-row`, `.bar`), BEM-light, no utility soup; the cascade is three layers (`tokens`, `base`, `components`) with `@layer`; a print stylesheet that drops the levers and expands the tables.
4. The script is progressive: on load it reads the embedded document or fetches it, hydrates the live parts, and does nothing the server did not already render; every DOM write uses `textContent` or built nodes, never `innerHTML` with data; the event source reconnects with backoff; errors go to `console.warn` with a code, never to the user as a stack.
5. The Mac app's web view loads `/?mode=app`; messages between the app and the page (theme, a request to focus a section) travel as query parameters and `data-` attributes, nothing more; the page must never depend on the app.
6. Types: the document has a pydantic model (`DashboardDocument`) that `document.py` builds and `templates.py` consumes, so a renamed field fails at import; the JSON schema in `docs/json.md` is generated from it.
7. The console's remaining pages (the log, the design page) share the same layer; the old `progress.py` HTML, the old `dashboard.py` CSS and the panel's inline page are deleted, not kept beside the new ones.
8. Screenshots for the README and the docs come from the visual tests (`scripts/screenshots.py`, Playwright, dev-only), light and dark, desktop and phone, from a seeded fixture database, so they are reproducible and never stale.

### The prompt: role, context and goal

You are building NAME for Mac: the same engine the open-source plan produced, wrapped in a native macOS application. Work on the owner's Mac in the checkout (`~/NAME`), with Xcode and the Python engine installed; the owner reviews after each stage and does the Apple-account steps himself.

What the app is, from the user's chair: download the DMG, drag NAME into Applications, open it. The goal: a 1.0 that a stranger installs in two minutes from a link, that runs for months without being thought about, that never shows a terminal, a path or a Python traceback, and that the owner uses in place of the launchd jobs on his own Mac from the day it ships.

### Constraints that hold throughout

1. The engine is the only brain. Every judgment, cut, count, rule and piece of text about the reading list comes from the Python package through its API; Swift holds presentation, process management and the system integrations (Keychain, notifications, login item, updates). If a feature needs logic, it is added to the package first, with its tests, and the app calls it.
2. Secrets live in the Keychain and nowhere else: never in `UserDefaults`, a plist, a log, a crash report, a diagnostics bundle, a screenshot of a settings pane or an API response. The engine reads them through `keyring` from the same Keychain items. The app never prints a key back, not even masked beyond the last four characters.
3. Fail open, visibly. When the engine is down, the app shows the last known state with its age and a plain sentence on what is wrong and what to press; it never shows a traceback, a port number or a path. Nothing in the app can cut articles without the engine's own confirmation step, and the engine's safety rules (the breaker, the budget, protected folders) are never bypassed from the app side.
4. One process tree. The app starts the engine, supervises it, restarts it after a crash with backoff, and stops it on quit; no launchd job of the engine's own remains while the app is installed. The engine's lock still protects against a CLI run at the same time.
5. Nothing phones home. No telemetry, no crash upload, no update check beyond Sparkle's appcast fetch, which the user can turn off. Network goes to BazQux, the model providers, healthchecks.io if configured, and the appcast; the entitlements say exactly that.
6. Native, quiet, accessible. The app follows the macOS Human Interface Guidelines: a menu bar extra, a standard Settings window, system fonts and colours, light and dark, Reduce Motion respected, every control reachable by keyboard and labelled for VoiceOver, no custom window chrome. The menu bar icon is a template image. Energy impact low: the app sleeps between the engine's runs.
7. The CLI survives. `NAME` on the command line works against the same data directory; "Install command line tool" places a symlink in `/usr/local/bin` with the user's permission; `NAME_HOME` points at the app's directory.
8. The owner's install migrates once, with consent, and can go back: the first launch offers to move `~/NAME` into Application Support, import `.env` into the Keychain, and remove the launchd jobs; "Undo migration" exists until the next release.
9. Verifiable. Swift code has XCTest coverage for every view model and the API client; the UI has tests for onboarding and settings; the engine's contract tests run against the bundled runtime; a release is cut only by the workflow, from a tag, with notarization passing.
10. Same voice, same rules as the open-source plan: plain words, one name per thing (the glossary), the commit trailers, ask before anything irreversible or costly, and never work on `main` directly.

### Stage A: the service contract

Outcome: everything the app needs from the engine exists in the Python package, documented and tested there, before a line of Swift is written. This stage is Python work in the main repository; the app is a client like any other.

1. `NAME serve --app --port 0 --token-file PATH --home DIR`: binds a free port on 127.0.0.1, writes `{port, pid, started}` as JSON to stdout's first line and to `DIR/serve.json`, reads the per-launch token from the file (the app writes 32 random bytes there with mode 600 before spawning), requires it as `Authorization: Bearer` on every request, and exits cleanly on SIGTERM and when its stdin closes (the app holds the pipe, so a dead app never leaves an orphan). `--app` also turns off the console's own browser-facing niceties the app replaces (no page shell, JSON only where the app asks for JSON).
2. Endpoints, all JSON with the versioned `schema` field, all documented in `docs/json.md` and covered by the contract tests: `GET /api/status`, `GET /api/dashboard`, `GET /api/list?band=&folder=`, `GET /api/why/{id}`, `GET /api/find?q=`, `POST /api/run` (`{mode: normal|shadow|sync, limit}`), `POST /api/stop`, `POST /api/pause` (`{until}`), `POST /api/mark` (`{id, kind}`), `POST /api/steer`, `POST /api/prune` (`{keep|fraction|below, dry_run}`), `POST /api/undo`, `POST /api/clear_old`, `GET /api/log?n=`, `GET /api/events` (server-sent events: phase changes, progress counts, run finished, attention needed, settings changed), `GET /api/settings` and `PUT /api/settings` (the whole config as JSON, validated by the same pydantic models, written to `config.yaml` with comments preserved), `GET /api/folders` (the account's folders and the policy for each), `POST /api/check/reader` and `POST /api/check/provider` (live checks for onboarding; cost in cents), `GET /api/profile` and `PUT /api/profile` (the student profile text), `GET /api/health` (version, uptime, schema version, data directory, last run, next run).
3. Keys through the Keychain: the engine's `keyring` extra is a hard dependency of the app build; the Keychain service name is `NAME` and the account names are the provider ids (`anthropic`, `openai`, ...) and `bazqux`; the app writes, the engine reads; `GET /api/keys` reports set or missing per provider, never a value; `.env` is read only if present and the app offers to import and delete it.
4. Attention states the app can show: `budget_reached`, `run_failed` (with the plain-language reason the engine already composes), `profile_rewritten` (Sunday, with the diff available at `GET /api/profile/diff`), `safety_tripped`, `reader_auth_failed`, `provider_auth_failed`, `update_available` (the app's own). Each is a field in `/api/status` and an event; each clears when the condition does or when the user dismisses it.
5. The bundled runtime: a `python-build-standalone` 3.12 interpreter (universal: one for arm64, one for x86_64, the app bundles both or the build makes two app variants) under `Contents/Resources/engine/`, with the package and its dependencies installed into it at build time from the released wheel, `NAME` as a console script inside it, every Mach-O signed with the hardened runtime and the entitlements the Python runtime needs (`com.apple.security.cs.allow-unsigned-executable-memory` only if a dependency needs it; test without). A `scripts/build_engine.sh` produces it reproducibly from a pinned wheel; its size is reported in CI (target under 60 MB per architecture).
6. Data directory: the engine accepts `--home`; `NAME_HOME` still works; the migration command `NAME migrate-home FROM TO` moves `config.yaml`, `data/`, `profile/` and the logs, rewrites nothing else, and is idempotent.
7. Tests in the package: the endpoint contract (every route, auth required, token rejected, `--app` behaviour, SSE delivers a run's phases, settings round-trip preserves comments, keys never in any response), `serve` exits on stdin close and on SIGTERM within 5 s, `migrate-home` on a copy of a real-shaped directory.

| Connections | Each with its fields, a Test button and a status line: healthchecks.io (ping URL); ntfy (topic URL); Pushover (user, token); Slack or Discord (incoming webhook URL); a generic webhook (URL, the events to send, a secret header); the Markdown or Obsidian note path for the weekly note; shell hooks after a run, after a cut and after the weekly rewrite (command, timeout, Run a test with a sample payload); the MCP server (on or off, the Claude Desktop and Claude Code configuration shown with Copy, the connected clients); publishing the console on the tailnet (the `tailscale serve` command shown and run with confirmation, the allowed host names); Apple Shortcuts (the App Intents the app offers: Run now, Pause, Open the list, Mark an article, Prune to N, Get today's list as text; Open Shortcuts); read-later services (Readwise Reader, Instapaper, Pocket) as hook templates with their tokens in the Keychain; export (JSON or CSV to a chosen folder after every run or weekly) |
| Appearance | Theme (system, light, dark); accent (the system accent or the app's); density (comfortable, compact); text size; the band colours shown as a preview; show lessons in the list; show the log in the window |
| Privacy and data | The data directory with Reveal in Finder, Change and Migrate; backups (daily on or off, keep N, Back up now, Restore from a backup); log level and how many days of logs to keep; the redaction filter (always on, shown); Export diagnostics; the statement that nothing is sent anywhere; Delete everything (the directory, the Keychain items, the login item, the schedule), with a typed confirmation |

Rules for every pane: a change applies when the field loses focus or Return is pressed, is confirmed by re-reading the engine, and can be undone with Command-Z within the pane; anything that writes to BazQux or spends money is a button that states what it will do and asks; help text under every field in the glossary's words, with the config key in `Advanced` view for those who want it; the Connections pane's Test buttons send one real message and report the answer in words; the schema is versioned so an older app shows an unknown field as a read-only line rather than hiding it; every pane has UI tests against the fixture engine, and the generic renderer has a test that every schema control type renders and round-trips.

### Stage C: packaging and distribution

Outcome: a tag produces a signed, notarized, stapled DMG and an appcast entry; a stranger's Mac opens the app without a warning; an existing install updates itself.

1. Signing: the app, the Sparkle framework and every Mach-O inside the bundled engine (the interpreter, every `.so` and `.dylib`) signed with the Developer ID Application certificate, hardened runtime on, entitlements limited to what the engine needs (network client; `allow-unsigned-executable-memory` and `disable-library-validation` only if proven necessary by a failing test, each with a comment saying why), timestamped. `codesign --verify --deep --strict` and `spctl --assess` pass in CI before notarization.
2. Notarization with `notarytool` using a Keychain profile the owner creates once (`xcrun notarytool store-credentials`); the ticket stapled to the app and to the DMG; the first-launch Gatekeeper experience tested on a clean user account.
3. The DMG: `create-dmg` with the app, an Applications symlink and a plain background; the file named `NAME-<version>-<arch>.dmg` or one universal DMG; SHA-256 checksums beside it on the release.
4. Sparkle 2: the `SUFeedURL` pointing at `https://github.com/OWNER/NAME/releases/latest/download/appcast.xml`, EdDSA signatures from a private key the owner keeps outside the repository (the public key in `Info.plist`), the appcast generated by `generate_appcast` in the release workflow from the DMGs, release notes from `CHANGELOG.md`; background checks daily, the user approves installs; a Check for updates item in the menu.
5. The release workflow (`.github/workflows/mac.yml`, macOS runner): on a tag `v*`: run the Python suite, build the engine from the released wheel of the same version (fail if the versions differ), `xcodebuild` archive, sign, notarize, staple, DMG, checksums, appcast, upload to the GitHub release, update the Homebrew cask in `OWNER/homebrew-tap` by pull request. Secrets in GitHub: the Developer ID certificate as a p12, its password, the notarytool API key, the Sparkle private key; documented in `docs/release.md` with the rotation steps.
6. Homebrew cask: `brew install --cask OWNER/tap/NAME`, with `auto_updates true` and the `zap` stanza listing Application Support, the Keychain items and the login item.
7. Universal binary: the Swift code builds universal; the engine is built twice (arm64 and x86_64 runtimes) and lipo-merged where possible or shipped as two engines selected at launch; the DMG tested on both architectures in CI (a `macos-13` Intel runner and a `macos-14` arm64 runner).
8. Version and build numbers: `CFBundleShortVersionString` equals the Python package version; `CFBundleVersion` is the build count; `NAME --version` inside the bundle prints both; the About box shows the engine's version and the data directory.
9. App Store readiness, noted but not done: an `App Sandbox` entitlement set, the engine as a bundled helper tool launched with `Process` is allowed in the sandbox, network client entitlement, Keychain access group; the parts that would need change (the `/usr/local/bin` symlink, the `~/NAME` migration outside the container) listed in `docs/app-store.md` for later.

### Stage D: tests and quality

Outcome: the app is tested at three levels, runs well on an old Intel laptop, and is usable without a mouse or with VoiceOver.

1. Unit tests (XCTest, `NAMETests`): the supervisor's state machine with a fake process (start, port parsing, health timeout, crash and backoff, give-up, quit order); the API client against the JSON fixtures the engine's own tests export (`tests/fixtures/api/*.json`, regenerated by the Python suite so both sides share one truth); the SSE parser (partial frames, reconnect); the settings store (round trip, validation errors mapped to fields); the Keychain wrapper against a test keychain; the migration planner (what moves where, idempotent).
2. Contract tests across the boundary: the Python package's `tests/contracts/test_app_api.py` runs every endpoint against `serve --app` with the token; the Swift client's fixtures are generated from that run, so a change on either side fails one suite or the other.
3. UI tests (`NAMEUITests`) against a fixture engine (a small Python script that serves canned responses for every endpoint and scripted events): onboarding end to end, each Settings tab, the menu bar menu's items and their actions, the reading list's context menu, the attention states, the engine-down state and recovery. Screenshots from the UI tests become the README's images.
4. A real run in CI: the macOS job builds the app with the real engine, launches it headless with `NAME_HOME` pointing at a fixture directory and the fake BazQux and model servers from the Python suite, and asserts `/api/health` and one full run through the app's supervisor.
5. Accessibility: every control has a label and a role; the window is fully keyboard-navigable; VoiceOver reads the menu bar state as a sentence; contrast at AA in both appearances; Reduce Motion and Increase Contrast honoured; the `accessibility-review` checklist run before 1.0.
6. Performance and energy: the engine idle under 100 MB and the app under 60 MB; CPU at idle near zero (no polling: events, not timers); the app's Energy Impact in Activity Monitor low over an hour of idling; a run on an Intel 2017 MacBook Air judges at the same cost and within 1.5x the time of the CLI; the engine's start-up under 3 s; the main window opens under 300 ms on cached data.
7. Failure drills, scripted: engine killed mid-run (the app shows the state, restarts it, the engine's own lock and pending-cut logic finish the work); the Mac sleeps during a run; the network goes away; the Keychain item is deleted while running (the next run reports provider auth failed and the app opens Settings); a corrupt `config.yaml` (the app shows the engine's validation message and offers the last good copy); a full disk; a second copy of the app launched; an upgrade over a running app (Sparkle's relaunch).
8. Crash resilience: the app's own crashes land in the system's crash reporter only; `Export diagnostics` includes the last one if the user chooses; no third-party crash SDK.
9. Code quality: SwiftLint with a short rule set, `swift-format`, the Swift concurrency checker on strict, no force unwraps outside tests, no `print`, `os.Logger` with privacy annotations (`.private` for anything that could carry an id or a title).

### Migration for the owner and for CLI users

Outcome: the owner's Mac moves from launchd jobs and `~/NAME` to the app in one consented step that can be undone; a CLI user who installs the app keeps a working CLI.

1. On first launch the app looks for `~/NAME` (and `NAME_HOME`), and for the launchd labels `NAME.*` and the old `com.antriksh.*`. If found, it offers: move the directory into Application Support (or keep using it in place), import `.env` into the Keychain and delete `.env`, unload and remove the launchd jobs, and install the login item. Each line a checkbox, all on by default, one Continue button; the summary names every path touched.
2. Undo migration (Advanced tab) moves the directory back, writes `.env` from the Keychain with the user's confirmation, and prints the `./install-launchd.sh` command to restore the jobs; it exists until the next major version.
3. The CLI inside the bundle is the same version as the engine; `Install command line tool` makes it `NAME` on the PATH; a `pipx` CLI already installed keeps working on the same data directory as long as `NAME_HOME` points there, and the app's lock and the CLI's lock are the same file, so they never run at once.
4. Config written by the app keeps the comments and order of the owner's `config.yaml` (the engine's settings writer is comment-preserving); nothing the app does not know is dropped.
5. The owner's live checks after migration, listed for him: the menu bar shows idle with the right unread count; Run now completes and the console in the window shows it; `NAME status` in Terminal agrees; the launchd jobs are gone (`launchctl print gui/$(id -u)/NAME.run` fails); the login item is on; a notification arrives on a forced failure (`Settings > Advanced > Simulate a failed run`).

### Working method

Stages in order: A is Python work in the main repository on a branch, merged by pull request before B starts; B, C and D on a `mac` branch under `mac/` with the app's own CI job; the owner's Mac is migrated only at the end of D, after the live checks.

1. Before each stage: re-read this document and `OPEN_SOURCE_PLAN.md`'s glossary; confirm Xcode, the signing identity and the notarytool profile are present (`xcodebuild -version`, `security find-identity -v -p codesigning`, `xcrun notarytool history`), and stop to ask for whatever is missing; the session never creates certificates or keys itself.
2. During: small commits with the trailers; `xcodebuild test` and the Python suite after every commit; the fixture engine kept in step with the real endpoints by the contract tests; every screen reviewed against the Human Interface Guidelines before it is called done; no third dependency without a reason in the commit.
3. What the owner runs himself, listed as a short checklist at the end of each stage: the first notarization, the first Sparkle update from the previous build, the Gatekeeper check on a clean account, the migration on his own Mac, and anything that spends money (the live checks in onboarding).
4. Reports after each stage, ten lines at most: what works, what the numbers are (test counts, bundle size, idle memory, start-up time), what the owner must do, what was deferred and why, the one decision needed next. The design doc in the Project gets the same.
5. Stop and ask when: an entitlement beyond network client seems needed; the engine would need a change that alters behaviour for CLI users; a dependency must be added; anything would touch the owner's data directory, Keychain or launchd jobs before the migration step; a cost above $1 for a live check.
6. Keep the CLI, the console and `pipx` users first-class throughout: the app must never need a feature that only the app can use.
