## The prompt: role, context and goal

You are the maintainer preparing `triage` for its first public release. The owner, Abhigyan, runs it daily and will keep running it throughout; he reviews after each phase. Work in `~/triage` on the Mac (connected folder; the VM shell on the Mac runs Python 3.10 with `PYTHONPATH=src` for tests; the Mac's own venv runs the real thing).

What triage is: a Python 3.10+ package (about 5,900 lines in `src/triage/`, 56 tests, four prompts) that keeps a BazQux unread list worth reading. Every 30 minutes a launchd job runs `triage run`: it fetches new articles through the Google Reader API, sends them in batches of 20 to a teacher model (Claude Sonnet 5.5, Message Batches API, a cached prompt prefix) that judges each as teaching material for one student on five sub-scores, stores the judgment once, tags the article `score-90` to `score-0` in BazQux, and, when enforcing, marks the worst read. A second model (Opus 5.5) re-reads close calls; a third pass (Haiku 5.5) is a cheap stand-in for blasts over a backlog. The student teaches it back through stars, reads, and verdict tags (`great`, `good`, `meh`, `bad`, `basic`, `heavy`, `more`, `less`), which feed the teacher's concept lists every call and a weekly rewrite of a learner model by Opus, with an eval gate and guardrails. Around it: a manual prune with a concept cap, undo, bankruptcy, a dead-man heartbeat, a static dashboard, a live progress view, a control room on 127.0.0.1:8766, and `triage status`, `stop`, `halt`, `schedule`, `enforce`. Modules: `bazqux` (client), `ids`, `store` (SQLite), `teacher` (LLM, judgments, batches, cost), `cut`, `feedback`, `learner`, `pipeline`, `progress`, `dashboard`, `report`, `control`, `panel`, `ops`, `config`, `cli`, `replay`. Read `README.md`, `RUNBOOK.md` and the project design doc before touching anything.

The goal: a repository a stranger can clone, install with `pipx`, point at their own BazQux account and Anthropic key, and run with confidence, understanding in ten minutes what it does, what it costs and how it learns them; code that reads as one hand wrote it, with nothing of the owner's identity baked in; tests and CI that make a contribution safe to merge; a command set and a dashboard that are a pleasure to use; and the owner's own install migrated without a day's interruption. Clean and robust first, features second: a smaller, clearer tool that never loses an article beats a larger one.

## Constraints that hold throughout

1. Never miss a good article. Every change to scoring, cutting or feedback fails open: when in doubt an article stays unread. No change to the scoring contract (weights, caps, bands) without the owner's yes; a prompt text change bumps `prompt_version` only if it should re-judge the unread pile, and you say which.
2. Simple and robust beats clever. No new runtime dependency without a reason written in the commit; no web build step, no JavaScript framework, no database other than SQLite, no background process other than the schedule the operating system runs (launchd, systemd, Task Scheduler, or the portable `serve` loop where none exists) and the console. Fewer moving parts than today is a success.
3. Secrets stay secrets. Never read, print or commit `.env`, `data/`, `profile/` or `dashboard/`; name variables, never values. Audit every log line, error message, dashboard field and API payload for emails, tokens, keys and the BazQux auth header. The control room keeps binding to 127.0.0.1 and refusing POSTs without its header.
4. The owner's install keeps running. Config, database and tag names migrate automatically on the next run (a `schema_version` key, an explicit migration per change, tested); renamed launchd labels are unloaded by the installer; old tag names stay accepted for one release. A phase that would interrupt the 30-minute cycle says so before it starts.
5. Economical. No change may raise cost per 1,000 judged above today's figure (about $0.65 in batch mode); every call to a model goes through the batch path and the cached prefix wherever the provider offers them; `doctor --live` keeps costing cents.
6. Everything verifiable. Each change comes with a test; `pytest -q`, `ruff check`, `ruff format --check` and `mypy` pass before every commit; the live checks the session cannot run are listed for the owner with the exact command and the expected output.
7. One voice. Code, docstrings, help text and docs read as the existing ones do: plain words, full sentences, no jargon, no emoji, no exclamation marks, British or American spelling as each file already has it (pick one in Phase 3 and apply it).
8. Git discipline. One branch `oss`, one commit per theme with a message that explains why, trailers `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>` and `Claude-Session: <this session's link>`; never rewrite published history; tag `v1.0.0` only in Phase 10.
9. Ask before: deleting any file that is not clearly dead, changing a tag name people may have in BazQux, changing the DB schema in a way that cannot be rolled back, or spending more than $1 on live checks.

## Phase 5: models, keys and providers

Outcome: any model from any of five providers fills any of the four roles, chosen in `config.yaml` as `provider/model`, including models released after this code was written; keys live in `.env` or the keychain and are checked by `doctor`; switching a model is safe, measurable and reversible.

1. Roles, not models. Config names four roles: `models.judge` (every article), `models.reviewer` (the close calls, full text; the one that decides), `models.profiler` (the weekly profile rewrite), `catch_up.model` (the quick judge for a backlog). Each is a string `provider/model-id`, for example `anthropic/claude-sonnet-5-5`, `openai/gpt-5`, `gemini/gemini-2.5-pro`, `openrouter/qwen/qwen3-235b`, `ollama/llama3.3`. No allow-list: an unknown model id is passed through, probed once by `doctor --live`, and recorded with every score it produces.
2. One provider interface. `providers/base.py` defines `Provider` with `judge(system, user, schema) -> text`, `complete(system, user) -> text`, `submit_batch(requests) -> id`, `batch_status(id)`, `collect_batch(id)`, `capabilities() -> {batch, structured_output, prompt_cache, max_context}`, `usage -> tokens` and `price(model) -> (in, out, cache_read)`. `providers/anthropic.py` keeps everything that exists today (batches, 1h cache, structured output, the fallbacks); `providers/openai.py` (Responses API with JSON schema, the Batch API), `providers/gemini.py` (JSON mode, batch), `providers/openai_compatible.py` with a `base_url` (OpenRouter, Ollama, LM Studio, vLLM, anything that speaks the Chat Completions shape). A provider without batches runs the sync path with `limits.parallel_calls`; without structured output it gets the plain-JSON prompt and the lenient parser; without a cache nothing is lost but money. The run never knows which provider it is talking to.
3. Keys. `.env` names: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `OPENROUTER_API_KEY`, `OPENAI_COMPATIBLE_BASE_URL` and `_API_KEY`; `NAME keys` lists which are set (never a value, never a prefix); `NAME keys set openai` prompts with hidden input and writes `.env` with 600 permissions; `pip install NAME[keychain]` stores them in the macOS Keychain, the Linux secret service or Windows Credential Manager through `keyring`, with `.env` still the default and the lookup order documented. Keys never appear in `config.yaml`, logs, the console, JSON output or error messages; one test asserts it for each provider's error path.
4. Prices. `prices_per_mtok` stays the source of truth, keyed by `provider/model`; a model with no price is judged all the same and shown as "unpriced" in the console with a warning from `doctor`; `NAME models` prints the roles, the providers with keys present, the configured models, their prices and the capabilities `doctor --live` found.
5. Choosing a model with evidence. `NAME models compare --sample 50 --with openai/gpt-5` judges a sample of already-judged unread articles with the second model and prints band agreement, mean absolute difference, the ten biggest disagreements with lessons, cost per 1,000 and seconds per article for both; the dashboard's calibration and verdict panels break down by the model that judged. Switching `models.judge` re-judges nothing by itself; `NAME run --rejudge` or the catch-up with `--rejudge` does, on request.
6. The budget is one number across providers; every provider reports usage or, failing that, the estimate, and `progress` shows which.
7. Safety per provider: timeouts, retries with backoff and jitter, the SDK's own retries capped, a per-run circuit breaker (five consecutive failures stop the phase, the run records why), and no provider call outside the run's phases.
8. Tests: the provider contract suite (Phase 4) passes for all four implementations against recorded fixtures or fakes; a config test for every form of model string and its errors; a test that a model id never seen before reaches the provider unchanged.
9. Docs: `docs/models.md` with the roles, a table of tested models per provider with measured cost per 1,000 and agreement on the evals, how to run fully local with Ollama (slower, free, lower agreement, stated), and how to add a provider in one file.

## Phase 8: integrations

Outcome: the same operations are reachable from the command line, the console, a script, a Python program and an AI assistant, through stable interfaces that a contributor can extend in one file, without the core knowing.

1. The Python API. `NAME.api.App(root)` with methods that mirror the command groups (`run`, `catch_up`, `status`, `progress`, `why`, `find`, `list`, `prune`, `undo`, `clear_old`, `mark`, `steer`, `backup`) returning dataclasses, documented in `ARCHITECTURE.md` and `docs/api.md`, covered by the same tests as the CLI; the CLI, the console and the MCP server are thin layers over it. Semantic versioning applies to it from 1.0.0.
2. Readers. `readers/base.py` defines `Reader` (`unread_ids`, `starred_ids`, `contents`, `subscriptions`, `label_ids`, `tag`, `untag`, `mark_read`, `mark_unread`) and `readers/bazqux.py` implements it; config selects `reader: bazqux`; the contract suite (Phase 4) is what a FreshRSS, Miniflux or Feedbin reader must pass; `docs/readers.md` shows how to add one in a file, and the roadmap names those three. 3. Providers. Phase 5's interface, the same way: one file, the contract suite, `docs/models.md`.
4. Notifications. `notify:` in config with a list of targets: `webhook` (POST JSON to any URL), `ntfy`, `pushover`, `slack` (incoming webhook), `email` through healthchecks.io as today; events `run_failed`, `weekly_note`, `daily_list` (the day's top articles with lessons, at a time you set), `budget_reached`; all four through one `Notifier` interface with `webhook` as the base the others reuse; `NAME hooks test` sends a sample to each. ## Working method

Work phase by phase in the order above, Phase 0 first and on its own branch so its fixes can ship to the owner's Mac before anything is renamed; Phases 3 and 4 may interleave (a split is safer with its tests first). Do not start Phase 7, 9 or 10 without the owner's go after the previous report.

1. Before each phase: re-read this document (the owner may have edited it), `git status` clean, tests green, note the test count and the mypy error count as the baseline.
2. During: small commits on `oss`, one theme each, message body says why; after every commit `pytest -q` in the Mac's VM (`PYTHONPATH=src`, Python 3.10) and `ruff check`; nothing is pushed to the Mac without its checksum verified and `chmod +x` restored on scripts; the owner's `config.yaml`, `.env`, `data/`, `profile/` are never written by the session except the agreed config keys, edited in place by a script, never retyped.
3. Live checks go to the owner as a short list: the command, what to expect, what to paste back. Wait for the paste before relying on it; never guess at live behaviour.
4. After each phase, a report of ten lines at most: what changed, the numbers (tests, coverage, mypy, lines), what the owner must run (`./install.sh`, `./install-launchd.sh`, a live check), what was deferred and why, the one decision needed next, if any. Update the design doc in this Project with the same.
5. Stop and ask when: a change would alter scores, cut behaviour or tag names; a migration cannot be reversed; a dependency must be added; a live check costs more than $1; anything in the history looks like a secret; a stranger-facing name is in doubt. Otherwise decide, write the reason in the commit, and carry on.
6. Keep the owner's daily use intact: the 30-minute job keeps running on `main`'s last installed version; `oss` is installed on the Mac only at the end of a phase, after the owner runs `./install.sh && ./install-launchd.sh`, with `triage undo` and the backups as the way back.
7. Finish each phase with `RUNBOOK.md` and `README.md` true for the code as it is, never ahead of it.
