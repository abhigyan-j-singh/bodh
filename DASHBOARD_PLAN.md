## How to use this prompt

This is the brief for the dashboard: the page behind the console, the static export, and the window of the Mac app. It replaces Phase 7 of the open-source plan (`OPEN_SOURCE_PLAN.md`) with a full specification and is the design the Mac app's window (`MAC_APP_PLAN.md`, Stage B) renders first through a web view and later natively. Run it in the open-source plan's order, after Phase 3 (one HTML layer) and Phase 6 (the JSON API), on the Mac or anywhere Python runs; nothing in it needs Xcode. A copy is committed as `DASHBOARD_PLAN.md`; open Claude Code in the checkout and say "read DASHBOARD_PLAN.md and start with the design system". `NAME` is the project's chosen name (today `triage`).

Decisions the prompt needs. Say nothing and the defaults apply.

| Decision | Default | Why |
| --- | --- | --- |
| Design direction | quiet, editorial, data-first: a reading-room feel, not a monitoring console; system fonts, generous whitespace, one accent, colour only where it carries meaning | the page is read a few times a day by one person deciding what to read; it should feel like a well-set page of a magazine, not an ops wall |
| Palette | neutral greys with one accent, plus a five-step band scale (90 to 100 down to 0 to 29) used everywhere a score shows; tokens defined once, light and dark | the band colours are the one meaning on the page and must be the same in a tag, a bar, a row and a chart |
| Charts | inline SVG drawn by the page's own script from the JSON; no chart library, no canvas, no external request | the project's rule of no build step and no framework; the charts are few and simple |
| Framework | none: one stylesheet, one script, HTML from the Python templates; progressive enhancement, the page reads without JavaScript | simplicity, parity between the three surfaces, and the Mac web view |
| Live updates | server-sent events from `/api/events` with polling as the fallback; the static export is a snapshot with its time stamped | fewer requests than polling, instant phase changes |
| Breakpoints | 390 px (phone over Tailscale), 768 px, 1100 px; the phone view is a first-class layout, not a squeeze | the owner opens it on the phone |
| Typography | the system stack (`-apple-system, BlinkMacSystemFont, Segoe UI, Inter, Roboto, sans-serif`) with a tabular-figure numeric style for numbers; no web fonts | no external request, native feel on every OS |
| Accessibility bar | WCAG 2.1 AA, keyboard complete, VoiceOver and NVDA checked, charts with text alternatives | a published app is used by people the author never meets |
| Name of the page | "NAME" in the title, the sections named by the question they answer | the page explains itself |

## The prompt: role, what exists, the standard

You are the designer and front-end engineer of NAME's dashboard. The page is served live by the console (`/`), exported as a static file after every run, and shown inside the Mac app's window; the same renderer must produce all three. Work in the checkout with the Python suite and Playwright available; the owner reviews after each stage, on his Mac and on his phone.

What exists today, judged from a fresh render on 11 October 2026 with seeded data (desktop 1280 px, phone 390 px, light and dark): one column of fourteen sections, 6,600 px tall on desktop. It opens with nine identical grey tiles (`unread now`, `score-90`, `score-70`, `score-50`, `score-30`, `score-0`, `spend today`, `spend 7 days`, `runner`) that wrap into two rows, named after tags rather than meanings, then a progress panel that repeats four of the same numbers (`judged today`, `arrived today`, `cut today`, `spend today`) and adds an unlabelled sparkline. The machinery (folders, batches, the log in a monospace box) comes before anything the reader cares about; the reading list, the most useful thing the engine produces, is not on the page at all. The flow chart is 1,100 px wide for fourteen days of data that occupy one column, with grouped bars 6 px wide, no values, dates as `09-28`, and swatches in grey, orange, red, blue and yellow that mean nothing elsewhere. The calibration table renders as a grid of dashes and zeros when empty instead of a sentence. Tables stretch to full width so a score on the left and its article on the right are 600 px apart; links are default blue and underlined; timestamps appear raw (`2026-10-11T11:26`); numbers are not aligned; the learnings section lists every article read this week as raw bullets with no cap. The dark render is identical to the light one: there is no dark mode. On the phone the tiles stack in pairs, the folder table wraps, and the flow chart shrinks to an unreadable 300 px. Three modules hold three copies of the CSS; the console page carries a fourth. None of the tables has a caption or scope; focus styles are the browser's defaults; nothing has a text alternative.

The standard: a page a demanding designer would ship under their own name. One idea per section, in the order the reader's questions arrive. Hierarchy you can read from across the room: one hero figure, a few stat tiles, then the list. Colour only where it carries meaning, and the same meaning everywhere. Charts that follow the data-visualization method (form first, colour by job, validated palette, thin marks, selective labels, a hover layer, a table twin), never decoration. Readable at 390 px and at 1440 px, in light and in dark, with VoiceOver, with the keyboard, with Reduce Motion. Honest empty states that say what will appear and when. Under 200 KB, no external request, rendered in under a second. Every number on the page traceable to one JSON document the engine serves, so the console, the export, the Mac app and anyone's script agree.

## Who it is for, and the five questions in order

The reader is one person, three or four times a day, usually for a minute, often on a phone, deciding whether to trust the engine today and what to read. Nobody is monitoring a fleet. The page therefore answers five questions, top to bottom, and a reader who stops after the first screen has the first three.

| Order | The question | The section | What answers it at a glance |
| --- | --- | --- | --- |
| 1 | Is it running, and is anything wrong? | State | one line: idle or the phase with a progress bar; the mode; the next run; one attention banner when something needs the reader, otherwise nothing |
| 2 | What happened since I last looked? | Today | the hero figure (unread now), four stat tiles (judged, cut, read, spend today) each with a 7-day sparkline and a delta against yesterday |
| 3 | What should I read? | The list | unread articles at 70 and above, best first, with band, lesson, concept, feed; filters by band and folder; links to the article and to BazQux |
| 4 | Is it judging well for me? | Your verdicts | grades against bands, the disagreements, calibration (read share by band), the near misses with a rescue action |
| 5 | What is it learning, and what does it cost? | Learning; Feeds; Money and machinery | this week's learnings by concept, the profile and its diff; feeds with sortable columns; cost per day and per 1,000, cache hit share, batches, runs, the log |

Two readers beside the owner shape the details: a stranger on the first day, who needs the empty states to teach ("Nothing judged yet. The first run submits your unread articles to the judge; their scores arrive within the hour."), and a contributor reading the JSON, who needs every panel to be a pure function of `/api/dashboard`.

Navigation: a sticky, unobtrusive section strip under the header on desktop (the five section names, the current one marked) and a bottom tab bar on the phone; anchors for each section so a notification or the menu bar can deep-link (`#list`, `#verdicts`). No sidebar on the page itself; the Mac app supplies its own.

## The design system

Outcome: every colour, size and distance on the page comes from a token defined once in `html.py` (the one HTML layer of the open-source plan's Phase 3) and emitted as CSS custom properties; nothing is hard-coded in a template or a script; light and dark are two value sets of the same tokens, each validated.

1. Colour roles, each a token: `--surface-1` (page), `--surface-2` (cards, table stripes), `--text-primary`, `--text-secondary`, `--text-muted`, `--line` (hairlines), `--accent` (one hue: links, the current section, the progress bar, the selected filter), `--accent-wash` (the accent at 10% for selection and hover), status `--good`, `--warning`, `--critical` (reserved for state, always with an icon or a word, never for a series), and the band scale `--band-90`, `--band-70`, `--band-50`, `--band-30`, `--band-0`: one hue stepped light to dark for an ordered scale (more is better reads as darker), with a text-safe companion for each step where a band is written as a chip. The de-emphasis grey `--series-muted` for context series in emphasis charts. Dark values are selected steps of the same ramps against the dark surface, declared under both `prefers-color-scheme: dark` (guarded so a light stamp wins) and `[data-theme="dark"]`; the page honours the OS and offers no toggle of its own beyond a `data-theme` hook the Mac app may set.
2. Validate the palette, do not eyeball it: the five band steps and the status trio must pass the lightness band, chroma floor, adjacent-pair colour-vision separation (OKLab ΔE ≥ 8 adjacent), normal-vision floor (≥ 15) and contrast checks in light and in dark; run the data-visualization validator (`validate_palette.js` from the dataviz method, with `--ordinal` for the band ramp) when the session has it, and record the report in `docs/design.md`. Text never wears a series colour; a chip's text is `--text-primary` on a wash of the band colour, and the band's name is always printed beside the colour.
3. Type: the system stack; sizes on one scale: 13 (table body, captions), 15 (body), 17 (section lead), 22 (section title), 48 (the hero figure, proportional figures, semibold); line heights 1.45 for prose, 1.25 for headings; `font-variant-numeric: tabular-nums` in table columns and axis ticks only; sentence case everywhere; no all-caps labels; weights 400 and 600 only.
4. Spacing on an 8-point scale (4 for inner chips): 16 inside cards, 24 between elements, 48 between sections; a content column of 720 px for prose and the list, 1100 px for tables and charts that earn the width, centred, 16 px side gutters on the phone; no card inside a card; cards only where grouping needs a boundary (stat tiles), otherwise whitespace and a hairline.
5. Shape and depth: 8 px radius on tiles and chips, 4 px on buttons and inputs; no shadows (a hairline `--line` border and the surface step do the work); no gradients; icons are a small inline set drawn as 16 px SVG paths (run, pause, stop, star, link, chevron, warning), stroke 1.5, currentColor.
6. Density: one table row 36 px on desktop, 44 px tap targets on the phone; tables under 640 px become stacked cards with the label and value pairs; charts keep their axis band inside their box so no inner scrollbars appear.
7. States, all designed, none left to chance: loading (a quiet skeleton on first paint only), refreshing (the previous render held at reduced opacity, no layout jump), stale (the "updated 12 min ago" stamp turns to `--warning` after two cycles and says why), empty (a sentence that says what will appear and what causes it), error (the engine's own plain sentence and the one action that helps), offline (the static export marks its time and that it is a snapshot).
8. Motion: 150 ms ease-out on opacity and transforms only; the progress bar's live animation and the sparkline's draw-in respect `prefers-reduced-motion` (then they just appear); nothing blinks, nothing scrolls by itself.
9. Accessibility built in: landmarks (`header`, `nav`, `main` with one `section` per question, each with an `h2`); a skip link; visible focus rings (`--accent`, 2 px, offset 2 px) on every interactive element; every table with a `caption` and `th scope`; charts as `figure` with a `figcaption` that states the finding and a "Show as table" toggle that reveals the data; colour never the only carrier (bands print their name, status has a word, the current filter has a check); contrast at AA for text and 3:1 for lines and icons; touch targets 44 px on the phone; the page reads in order without CSS.
10. The tokens, the type scale, the spacing scale, the icon set and the states live in `docs/design.md` with one screenshot per state, and in a `/design` page the console serves in development that shows every token and component on one screen (the living style guide the visual tests screenshot).

## The panels

Each panel is one function of the JSON, with its own empty state and its own test. In order on the page:

1. **Header and State.** The name, the time of the data ("as of 16:56", relative on hover: "4 min ago"), and the state line: `Idle · next run in 22 min` or `Judging 240 of 1,200 · 90 a minute · about 11 min left` with a thin progress bar in the accent; the mode as a chip (`Scoring only` or `Cutting below 35`); the levers (Run now, Stop, Pause) in the console and the app, absent in the export. Below it, when needed, one attention banner (`--warning` or `--critical` with an icon and a word): budget reached, a run failed (the reason, one line), the safety limit tripped, sign-in failed, the Sunday profile rewritten (with a link to the diff). Never more than one banner; the most severe wins; a dismiss control for the ones that are information.
2. **Today.** The hero figure: unread now (48 px) with the target beside it in secondary text (`130 unread · target 40`). A row of four stat tiles: judged today, cut today, read today, spend today, each with its value, a delta against yesterday (signed, coloured by direction and whether up is good) and a 7-day sparkline in `--series-muted` with today in the accent. On the phone the tiles become a 2x2 grid. No second row of tiles anywhere on the page.
3. **The list.** The section the owner opens the page for. A filter row above it (band: 90+, 70+, 50+; folder: all or one; sort: score, newest), one row per unread article at or above the chosen band, best first: the band as a chip with its number (`92`), the title as the link (the article's own URL), the lesson in one line, the concept and the feed in secondary text, the age ("2 h"), and a quiet "BazQux" link. In the console and the app each row has a verdict menu (great, good, meh, bad, basic, heavy, more, less) calling `/api/mark`, shown on hover and on focus, and a keyboard shortcut per grade when a row is focused. Capped at 50 rows with "Show 50 more". Empty state: "Nothing at 70 or above right now. 34 articles are waiting for the judge; the next run is in 22 minutes."
4. **Your verdicts.** Three parts. A compact grades-by-band grid (the five bands as rows, great/good/meh/bad as columns, cells shaded on a sequential wash by count with the number printed) with one sentence of reading under it ("Your great and good fall mostly in the 70+ bands: the judge is calibrated to you" or the honest opposite). The disagreements list (your grade, the score as a band chip, the title, the concept), at most ten. Calibration: a horizontal bar per band showing the share read and the share starred (two series, legend, direct labels at the bar ends, the bars in one hue and its lighter step), with the sentence that explains what a good shape looks like. Then the near misses: the best of what was cut this week, with a Rescue action (the `rescue` verdict) in the console and the app. Empty state per part.
5. **Learning.** This week's learnings grouped by concept, capped at five concepts and five lines each with "and 12 more", each line the title and its lesson; the concept map as a tag cloud of the last 90 days sized by count (text at 13 to 17 px, never smaller, in `--text-primary`, counts in `--text-muted`), the frontier (concepts seen at 70+ this fortnight and not yet read) marked; the student profile in a collapsed block with its version and date and a "Show the Sunday diff" toggle rendering the diff with added and removed lines marked by a symbol and a wash, not colour alone.
6. **Feeds.** The last 30 days as a table: feed, folder, articles, mean score as a band chip, cut share, read share, starred share, with sortable column headers (a visible sort indicator, `aria-sort`), the proposals from the monthly report shown as a short line under a feed when one exists. Rows capped at 40 with a filter box. On the phone: cards with the four numbers in a 2x2 grid.
7. **Money and machinery.** Cost: a 30-day column chart of spend per day (one series, one hue, selective labels on the maximum and today, hairline grid, the daily budget as a labelled reference line) and three stat tiles (cost per 1,000 judged, cache hit share, spend this month). Machinery: batches in flight as a short table (purpose, articles, age), the last 20 runs (started, kind, ok with a word and an icon, the summary in one line, expandable), and the log tail in a `pre` with wrap, 10 lines, a "Show 200" control in the console only. The export carries no log.
8. **Footer.** Version, data directory (console and app only), links to the docs and the repository, "Exported 16:56" on the static file.

## Charts: the rules for every chart on the page

The page has four charts (the stat-tile sparklines, the calibration bars, the grades grid, the spend columns) and one meter (the progress bar). Each follows the data-visualization method in this order: form first, colour by the job it does, the palette validated, marks and spacers to spec, a hover layer, a table twin, then look at the render. When the session has the `dataviz` method and its validator, use them; the rules here are the ones that bind either way.

1. Form by job: a single value with a trend is a stat tile, never a one-bar chart; a share by band is a bar (horizontal when the labels are words); a count over days is a column chart; parts of a whole are a stacked bar, never a pie; two measures of different scale are two charts, never a second axis. The flow chart of today (five grouped series over 14 days) becomes the four sparklines in the tiles plus the one spend chart; nothing on the page shows more than two series at once.
2. Colour by job: the band scale is an ordinal ramp of one hue, used for the chips, the grades grid and nothing else; a single series takes the accent; context takes `--series-muted`; status colours never appear on a series. Categorical hues are assigned in a fixed order and never cycled; this page needs at most two.
3. Marks: bars at most 24 px thick with a 4 px rounded data end and a square baseline; a 2 px surface gap between touching bars and stacked segments, never a stroke; lines 2 px with round joins; end markers at least 8 px with a 2 px surface ring; area fills at 10% opacity; grid and axes as solid 1 px hairlines one step off the surface, never dashed; axis ticks on round numbers, compact from 1,000 (1K, 2K).
4. Labels: a title that states the finding, not the topic ("Spend is under the budget every day this month"); direct labels selectively (the maximum, today, the end of a line), never on every point; a legend whenever two series share a chart, none for one; text in text tokens, never in the series colour; a label that does not fit moves outside the mark or to the tooltip, never clipped.
5. The hover layer ships with every chart: a crosshair snapping to the nearest day on the spend chart, a per-mark tooltip on bars and cells, the same readout on keyboard focus, a hit target of at least 24 px around small marks; values lead, labels follow in the tooltip; names inserted with `textContent`.
6. A table twin for every chart, behind "Show as table", carrying every value the chart shows; the chart is never the only way to read a number.
7. The sparkline: 7 points, the last in the accent with a ring, the rest in `--series-muted`, no axes, the tile's value and delta carry the numbers; 40 x 16 px on the phone, 72 x 20 on desktop.
8. The progress bar is a meter: the fill in the accent, the track a lighter step of the same hue; the numbers printed beside it, never only the bar.
9. No chart on the page animates data; a draw-in on first paint only, off under Reduce Motion.
10. Render and look: every chart has a Playwright screenshot in light and dark at 390 and 1280 px in the visual tests, and the review checklist (below) is applied to each before it is called done; anything matching the method's anti-pattern list (dual axes, recolour on filter, cycled hues, numbers on every point, clipped labels, a fixed height that cuts the axis, a pie for close values, colour-only encoding) is a failed review.

## Live behaviour, the data contract, performance

1. One document feeds everything: `GET /api/dashboard` returns `{schema: 1, as_of, state, today, list, verdicts, learning, feeds, money, machinery}` with every number the page shows and nothing it does not; the static export embeds the same document in a `<script type="application/json">` block and renders from it; the Mac app reads the same route. The document's JSON schema lives in `docs/json.md` and a test validates each render against it. Numbers arrive as numbers, dates as ISO strings, texts already composed by the engine (the state sentence, the attention reason, the calibration sentence), so the page never invents words.
2. Live updates: the console page subscribes to `/api/events`; a `progress` event updates the state line, the bar and the tiles in place; a `run_finished` event refetches the document; `attention` events update the banner; the page falls back to polling every 30 s when events are unavailable and says so in the footer. The export is a snapshot and says "Exported at 16:56; open the console for live data".
3. Freshness: "updated 12 s ago" in the header, ticking; after two missed cycles the stamp turns to the warning colour and the state line says the engine is not answering; the last render stays on screen at full opacity (it is still true) with the age made plain.
4. Refetch keeps the frame: on refresh the page holds the previous render and swaps nodes in place; no skeleton after the first paint, no scroll jump, no flashing numbers; a changed number briefly carries a wash that fades in 300 ms (off under Reduce Motion).
5. Budgets, enforced by tests: the HTML with its inline CSS, script and JSON under 200 KB for a 50,000-article database (the list capped at 50 rows, learnings and feeds capped); first contentful paint under 300 ms on a 2017 laptop; full render under 1 s; no request to any host but the console's own; the document built by the engine in under 250 ms at 50,000 articles (queries indexed, the heavy aggregates cached for 60 s).
6. Caching on the engine: the dashboard document is computed once per change (a run finishing, a verdict recorded, a settings change) and served from memory between; the export is written only after a run.
7. The page works without JavaScript: the server renders every panel from the same document; the script adds the live layer, the filters, the tooltips and the verdict menus. The filters and the "Show as table" toggles are plain links and buttons that work with the keyboard and without a pointer.

## Code architecture

Outcome: one place for the markup, one stylesheet, one script, one data document; the console page, the static export and the Mac app's web view are the same page with three flags.

1. `NAME/web/` holds `tokens.py` (the design tokens as a Python dict, rendered to CSS custom properties, the single source for the validator and the docs), `templates.py` (small functions that return HTML for each panel from a typed slice of the document: `header(doc)`, `today(doc)`, `article_list(doc, interactive)`, and so on, each under 60 lines, each escaping through one `esc`), `dashboard.css` (one file, under 600 lines, mobile first, no preprocessor), `dashboard.js` (one file, under 400 lines, plain ES2020, no framework, no build step: the event source, the renderers for the live parts, the tooltips, the filters, the verdict menu), `icons.py` (the inline SVG set) and `document.py` (builds the JSON document from the store: the only module that touches SQL, with one function per panel and the 60-second cache).
2. Three outputs from one render function: `render(doc, mode)` where mode is `console` (levers, verdict menus, the log, the live script), `export` (no levers, the embedded JSON, the snapshot stamp) or `app` (the console without the page chrome the Mac window supplies, with a `data-theme` hook). The test asserts the export equals the console minus a known set of nodes.
3. CSS written against roles, never values; class names by component (`.tile`, `.chip`, `.list-row`, `.bar`), BEM-light, no utility soup; the cascade is three layers (`tokens`, `base`, `components`) with `@layer`; a print stylesheet that drops the levers and expands the tables.
4. The script is progressive: on load it reads the embedded document or fetches it, hydrates the live parts, and does nothing the server did not already render; every DOM write uses `textContent` or built nodes, never `innerHTML` with data; the event source reconnects with backoff; errors go to `console.warn` with a code, never to the user as a stack.
5. The Mac app's web view loads `/?mode=app`; messages between the app and the page (theme, a request to focus a section) travel as query parameters and `data-` attributes, nothing more; the page must never depend on the app.
6. Types: the document has a pydantic model (`DashboardDocument`) that `document.py` builds and `templates.py` consumes, so a renamed field fails at import; the JSON schema in `docs/json.md` is generated from it.
7. The console's remaining pages (the log, the design page) share the same layer; the old `progress.py` HTML, the old `dashboard.py` CSS and the panel's inline page are deleted, not kept beside the new ones.
8. Screenshots for the README and the docs come from the visual tests (`scripts/screenshots.py`, Playwright, dev-only), light and dark, desktop and phone, from a seeded fixture database, so they are reproducible and never stale.

## Copy: the words on the page

1. Every section title is the question it answers in the reader's words, sentence case: "What happened today", "What to read", "Is it judging well for you", "What it is learning", "Your feeds", "What it costs and how it runs". Under each title, one sentence of lead that states today's answer from the document ("Nothing needs you. 38 judged, 12 cut, 7 read."), never a description of the panel.
2. Numbers carry units and context: `$0.41 today`, `90 a minute`, `about 11 min left`, `2 h ago`; thousands separators; two decimals for money, none for counts; percentages as whole numbers with the base in a tooltip ("26% cut (5 of 19)").
3. Dates and times in the reader's zone, never ISO: "16:56", "yesterday 09:10", "Mon 6 Oct"; relative when under a day, absolute on hover.
4. Empty states teach and promise: what will appear, what causes it, when ("No verdicts yet. Tag an article great, good, meh or bad in BazQux; it shows here after the next run, within 30 minutes."). Never a bare dash, a zero table, or "No data".
5. Errors are the engine's own sentence plus the one action: "BazQux did not answer (403). Check the password in Settings." No codes without words, no stack traces, no "something went wrong".
6. Confirmations for anything that writes to BazQux state the number, the mode, the reversibility and the cost of time: "Cut 50 of 130 unread articles below 35? Reversible with Undo; it takes about a minute." Buttons name the action ("Cut 50"), never "OK".
7. The glossary of the open-source plan's Phase 2 is the vocabulary: one word per thing (judge, review, cut-off, scoring only, catch-up, rescue), the same in the page, the CLI and the docs; no internal words (kv, inflight, stand-in, bucket) reach the page.
8. Tone: plain, short, warm, no exclamation marks, no emoji, no jargon, British spelling; the `ux-copy` review (empty states, errors, confirmations, button labels) run over the whole page before 1.0 and its findings fixed.

## Quality bar and testing

1. Visual regression: Playwright screenshots of the whole page and of each panel, from a seeded fixture database with every state reachable (idle, running, attention, empty, stale, error), at 390, 768 and 1280 px, light and dark, Reduce Motion on; stored under `tests/visual/` and compared with a 0.1% pixel tolerance in CI on Linux (WebKit, Chromium) and macOS (WebKit, the Mac app's engine); a change to a screenshot is reviewed like code.
2. Accessibility audit: `axe-core` run through Playwright on every state with zero violations at AA; a keyboard script that tabs through the page and asserts the focus order matches the reading order and that every interactive element is reachable and operable with Enter and Space; VoiceOver on macOS and NVDA on Windows checked by a person once before 1.0 with the findings fixed; the `accessibility-review` checklist (contrast, keyboard, touch targets, screen reader) completed and kept in `docs/design.md`.
3. Budgets in tests: page size, time to render, request count (one), the document build time at 50,000 articles, JavaScript size; a 3x regression fails CI, a 1.5x regression warns.
4. Browsers: Safari and WebKit first (the Mac, the phone, the app's web view), then Chromium and Firefox current; no polyfills; features used only if available in all three for two years.
5. Content tests: every empty state renders its sentence; every number in the page appears in the document (a test walks the rendered text for digits and finds each in the JSON); dates render in the configured zone; the export equals the console minus the known nodes; the `app` mode has no page chrome; no secret, email or path from `.env` or the data directory reaches the page (the regex check from the open-source plan).
6. Design review before a panel is called done, written as a checklist in the pull request: one idea per panel; the lead sentence true and specific; hierarchy visible at a glance (squint test); alignment to the grid; the type scale and spacing scale only; colour carrying meaning only, the same meaning everywhere; the chart form right for the job and clean of the anti-pattern list; labels sparing and unclipped; the phone layout designed, not squeezed; dark mode selected, not inverted; every state seen in a screenshot; copy in the glossary's words.
7. The adversarial look: after each panel, a fresh reviewer (a subagent when available, otherwise the author a day later) is handed the screenshot and the JSON and asked what a demanding designer would change; the three largest findings are fixed before the next panel starts.
8. A stranger test for the page alone: a person who has never seen the engine is shown the page for 30 seconds and asked what is running, what happened today and what they would read; three of three answered without help is the bar.

## Acceptance criteria

- [ ] The page answers the five questions in order; the first screen on a 1280 px display holds the state line, the hero figure, the four tiles and the top of the list; nothing on the page repeats a number shown elsewhere

## Working method

Order: the design system first (tokens, type, spacing, states, the living `/design` page, validated), then the document and its schema, then the panels in page order, one at a time, each with its template, its CSS, its live behaviour, its tests and its screenshots, each reviewed before the next; the Mac app's `app` mode last.

1. Before starting: re-read this document and the glossary; render today's page from the seeded fixture and keep its screenshots as the "before"; confirm Playwright and the browsers are installed; confirm the open-source plan's Phase 3 (one HTML layer) and Phase 6 (the JSON API) are merged, and stop if not.
2. During: one commit per panel with its screenshots; the design review checklist in every pull request; no new dependency (the page has none and keeps none); the `dataviz` validator run on every palette change; the owner shown each panel on his phone before it is called done.
3. Decisions the session makes alone: anything inside the rules above. Decisions it brings to the owner, with two screenshots side by side: the accent hue, the exact band ramp, the section titles' wording, the tile set in Today, the list's default band, and anything that would change what the engine computes.
4. Report after each panel in five lines: the screenshot links, the numbers (size, render time, axe violations), what the reviewer changed, what is next.
5. Stop and ask when: a panel needs a number the engine does not produce (add it to the engine with a test first, through the open-source plan's rules); a rule here conflicts with the Human Interface Guidelines in the Mac app's web view; the budget cannot be met without dropping content (bring the trade-off, do not quietly drop).
